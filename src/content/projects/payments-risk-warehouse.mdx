## The problem

Before a payments company can build fraud models or trustworthy risk reporting, it needs a solid
data foundation:
- clean models of the core entities (transactions, accounts, devices, logins, disputes);
- metric definitions everyone agrees on;
- features that don't quietly leak information from the future into training data;
- monitoring that catches bad data before it reaches a decision.

This project builds that foundation end to end for a peer-to-peer payments product, on public,
synthetic data. The outputs are a dimensional warehouse for analysts and a point-in-time-correct
feature table for a fraud model.

## The data

- **Transactions: [PaySim](https://www.kaggle.com/datasets/ealaxi/paysim1)**, a synthetic
  mobile-money dataset of about 6.3 million transactions with fraud labels. It has quirks I handle
  explicitly rather than paper over:
  - `step` is an hour index (about 30 days), not a timestamp. I derive `transaction_ts` from a
    fixed anchor date, kept in a dbt variable so output is reproducible.
  - Fraud only occurs in `TRANSFER` and `CASH_OUT` transactions.
  - Merchant accounts (IDs starting with `M`) have no balance information.
  - Balance fields are often inconsistent with the transaction amount.
  - `isFlaggedFraud` is a legacy rule-based flag, which makes a useful baseline to compare against.
- **Accounts, devices, logins and disputes** are generated by a seeded Python script, so the output
  is the same on every run. They cover the identity, account-access and dispute domains that PaySim
  lacks: signup date, KYC status and country per account; devices; login attempts with success,
  device and IP country; and disputes linked to a subset of transactions, weighted towards fraudulent
  ones.

All data is synthetic. No real customer data is used.

## Architecture

```text
 PaySim CSV ─┐
             ├─► ingestion (Python) ─► DuckDB `raw` ─► dbt staging ─► intermediate ─► marts
 Synthetic   │                                                         (features)     ├─ core: dim_* / fct_*
 entities ───┘                                                                        └─ ml:   ml_transaction_features
                                                    dbt tests + docs (lineage, data dictionary)
```

| Layer | Purpose | Examples |
|---|---|---|
| Staging | One model per source: rename, cast, clean. No joins. Views. | `stg_paysim__transactions`, `stg_app__logins` |
| Intermediate | Joins and risk features. Views. | `int_account_velocity`, `int_device_sharing` |
| Marts / core | Star schema for analytics. Tables. | `fct_transactions`, `dim_account`, `dim_device` |
| Marts / ml | ML-ready, leakage-safe features. Tables. | `ml_transaction_features` |

The star schema has three facts, each with a stated grain:
- `fct_transactions`: one row per transaction, built incrementally.
- `fct_logins`: one row per login attempt.
- `fct_disputes`: one row per dispute.

They share four dimensions: `dim_account`, `dim_device`, `dim_date` and `dim_transaction_type`.

Every model has a YAML entry with a description, its grain and column descriptions. Those feed the
dbt docs site, which doubles as the data dictionary and lineage graph.

## Modeling decisions

**Point-in-time features.** Every feature in `ml_transaction_features` may use only information
available *before* the transaction it describes. That covers:
- velocity per account (count and amount over 1 hour, 24 hours and 7 days);
- account age at transaction time;
- amount compared with the account's trailing average;
- devices per account and accounts per device;
- failed logins before the transaction;
- prior disputes.

A dedicated singular dbt test asserts this rule, because label leakage is the easiest way to build a
fraud model that looks great offline and fails in production.

**Flag, don't drop.** PaySim's inconsistent balances are kept and flagged (`has_balance_mismatch`)
instead of filtered out. In risk data, anomalies are often the signal, so the flag is a candidate
feature in its own right.

**Incremental fact table.** `fct_transactions` builds incrementally on `transaction_id`, the way
high-volume event data is processed in production, rather than rebuilding the whole table on every
run.

**Portable SQL.** Models run on DuckDB locally but stick to ANSI SQL that would move to Snowflake
with minimal changes. Any dialect-specific function is called out in a comment.

**Simple over clever.** The SQL is written to be read and explained, not to be as short as possible.

## Data quality

- Every primary key is `unique` and `not_null`; every foreign key has a `relationships` test.
- `accepted_values` on enumerations: transaction type, KYC status, dispute status.
- Range checks with `dbt_expectations` or singular tests: amounts greater than zero, timestamps
  inside the data window.
- The leakage test on the ML feature table.
- Severity matches the problem: `warn` for known PaySim quirks such as balance mismatches, `error`
  for real integrity breaks.
